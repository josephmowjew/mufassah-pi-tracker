Read this first — five defects that are live right now

These are not style opinions. Each was confirmed in source and each one either breaks a headline feature or exposes the system to abuse.

  1. Geofence alerts never fire. The entry/exit event write uses column names that don't exist on the model, and the notification is called with the wrong number of arguments. The INSERT fails and, even if it didn't, the constructor would throw. This is the core theft-protection feature.
  2. Suspended accounts can still log in. suspended_at is written by the admin suspend action and never read by anything. Suspension currently does nothing.
  3. The PayChangu webhook fails open. If PAYCHANGU_WEBHOOK_SECRET is unset, the signature check is skipped entirely — any unauthenticated caller can mark payments as completed and activate subscriptions.
  4. The device credential file is committed to git. mufassah-tracker/config.env is tracked, and the README instructs operators to edit it in place. The moment anyone does, the live device token enters git history.
  5. Anonymous visitors get bounced to the staff login page. A notification component is mounted outside every route guard on the public marketing site, fires an unauthenticated request, receives a 401, and the interceptor hard-redirects to /login.

The shape of the problem

The backend is functionally broad — 40+ models, 50+ controllers, 375 tests — but its integration seams are untested. The geofence bug survived precisely because the test builds GeofenceEvent rows with a factory and never exercises the real POST /iot/location path. That's the pattern: unit coverage is good, cross-layer wiring is not.

The frontend has strong bones — every one of 49 routes is lazy-loaded, TypeScript is strict with almost no any, and there's no dangerouslySetInnerHTML anywhere. Its problem is the opposite: a well-built UI kit and error helper exist but are used in 6 files out of ~128, so consistency decays screen by screen.

The tracker is a single 691-line file with no tests, deployed to hardware you can't easily reach. It has no idempotency keys, so a dropped response after a successful write produces duplicate points; and a permanent 401 is retried forever, which eventually overflows the buffer and silently deletes history.

02  Suggested sequencing

The order matters more than the individual fixes. Phase 1 is deliberately small: it closes live holes without touching architecture, so it can ship inside a day and be verified immediately.

Phase 1 — Close the live holes (about a day)

Fix the geofence write and notification call, gate login on suspended_at, make the webhook signature check fail closed, untrack config.env and rotate the token, and guard the global notification component behind isAuthenticated. Add a regression test that drives the real POST /iot/location endpoint.

Why first: every item is a localised change with no schema migration and no API contract change. Users see the geofence feature start working the same day.

Phase 2 — Stop the self-inflicted load (2–4 days)

Replace the per-device polling fan-out on the tracking pages with a single batched endpoint; cap per_page everywhere and add the composite indexes; collapse the branch dropdowns onto one canonical query; push the report aggregations into SQL.

Why second: the tracking pages currently generate over a hundred requests per client per 30 seconds. That's a capacity ceiling on the whole platform, and it also happens to be the single biggest perceived-speed win for customers.

Phase 3 — Make failures visible (1 week)

Add the missing onError handlers, a real 419 retry, an axios timeout, an offline banner, and network-aware error messages. Add a global exception handler that logs and never leaks provider text.

Why third: these are cheap individually but there are many of them, and they depend on Phase 1 not changing the error contract underneath them.

Phase 4 — Pay down the structure (ongoing, behind feature work)

Adopt the UI kit and the shared error helper across all screens, extract services from the fat controllers, delete the empty scaffolding directories, split the monolithic pages, and add tests to the community bounty flows before the next money-touching change.

Why last: these are real but they don't change what a user experiences this week. Doing them first would delay the fixes that do.

03  What's already working well

Worth stating plainly, because these are the things the rest of the codebase should be pulled toward — not replaced.

  • Route-level code splitting is complete. All 49 pages use React.lazy, so Leaflet and Recharts only load on the routes that need them. This is better than most production React apps.
  • TypeScript discipline. strict, noUnusedLocals, noUnusedParameters are all on, and there are only about ten real any usages across 128 files.
  • Secrets are correctly handled on the API. UserResource hides password, national ID and 2FA secret; IotModule hides api_token behind a hashed cast. The token is never logged anywhere in the tracker either.
  • The tracker's core resilience design is sound. SQLite offline buffering, GPS accuracy gating, connectivity pre-checks, graceful shutdown, and a heartbeat thread are the right architecture for a field device — the defects are in the edges, not the design.
  • useFamilies.ts has a proper query-key factory. It's the one place doing it right, and it's the pattern the other 373 inline query keys should follow.
  • DeviceDetailPage.tsx is the model screen — real "not found" state, confirm dialog, toast feedback. New screens should be built by copying it.
